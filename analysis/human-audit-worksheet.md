## 2. Audit Method

The audit uses `eshop-sut/api_specification.md` as the authoritative source, followed by the verified test basis, domain model, BVA analysis, test design, coverage matrix, and Prompt 006 scope audit. No implementation source, README behavior, frontend validation, database, runtime behavior, Postman suite, or API result was inspected.

Each case was checked for existing TB/EP/blocker references, preserved scope, requirement support, deterministic-oracle support, abstract preconditions, exploratory quality, and logical overlap. BVA is N/A for every case because Prompt 004 established no executable specification-backed boundary. SEC references are N/A for non-security cases and explicitly MISSING for security-relevant cases because the SEC catalog is absent.

For requirement-support question C, the per-case assessment is `NO` for TC-API-001–129: no case asserts an undocumented rule as a hard expectation. Cases that investigate undocumented behavior remain BLOCKED or EXPLORATORY_ONLY instead. Question D is represented by each row's `Duplicate Status`.

`AI Review Recommendation` remains advisory evidence only. `Student Decision` and `Student Correction Decision` were populated strictly from the student's supplied lists, and `Student Reason` was populated strictly from the six student-supplied reason patterns.

The AI recommendation and AI reason were produced before student review. The completed Student Decision, Student Reason, and Student Correction Decision fields are the authoritative audit record.
